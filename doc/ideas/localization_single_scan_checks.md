# 1 枚のスキャンを使う自己位置の判定を、地図の質が合う環境で試す

## 背景

自己位置の監督 ([localization_supervisor](../../localization_supervisor/README.md)) の判定のうち、1 枚のスキャンを地図に重ねるのは `scan_map` だけにしている。
次の 2 つの判定を作って評価したが、屋外の地図 (別の走行で作った地図。植栽や柵のすき間から先が見える) では、正しい姿勢と異常を区別できなかったので、コードごと外した。

| 判定 | 見るもの | 屋外の地図で区別できなかった理由 |
| :--- | :--- | :--- |
| 光線の突き抜け (`freespace`) | センサから端点までの光線が、地図の占有セルを越えている割合。見えるはずの壁が見えない状態を捉える | 正しい姿勢でも、植栽や柵の向こうが見えるので、突き抜ける光線が多い (例: 2〜7 割)。地図に壁として残っているものと、スキャンに見えるものが一致しない |
| 少しずつのずれ (`scan_drift`) | 新しいスキャンごとに、地図に最もよく合うずらし量を求め、直近の一定時間の平均の長さと向きのそろい方を見る。ずらし量が増えていく傾向 (傾き) も条件にできる | 地図の位置合わせがずれているため、正しい姿勢でも、ずらしたほうが合う向きがほぼ一定になる |

今の扱い:

- 1 枚のスキャンの判定は `scan_map` (一致率を、正常なときの中央値と比べる) だけ。広い範囲を見る `submap_map` と組み合わせる ([design.md](../../localization_supervisor/doc/design.md))。
- 少しずつのずれは、GNSS との食い違い、`submap_map`、AMCL と EKF の差で捉えている。

## 構想

次のような環境では、2 つの判定が効く見込みがある。

- 室内や倉庫など、壁が閉じていて、地図とセンサで見える形が一致する環境 (光線の突き抜けが、正しい姿勢でほぼ 0 になる)。
- 走行に使う LiDAR で作り直した地図 (位置合わせのずれが小さい)。

案:

- 判定を、`localization_supervisor` の標準の判定として戻す。戻すのは、削除したコミットの前の版 (`core/detectors/freespace.py`、`core/detectors/scan_drift.py`、`core/grid.py` の `ray_penetration`) をもとにする。
- 外部の判定として、そのロボットのパッケージに置く。プラグインの約束 ([plugins.md](../../localization_supervisor/doc/plugins.md)) で足せるので、フレームワークは変えない。

## 入る場所

- 判定のプラグイン: `core/detectors/` に足し、`STANDARD_DETECTORS` に登録する。
- 設定: `detectors` に重み 0 のインスタンスを定義し、記録だけを取る。

## 着手の前に確かめること

- 対象の環境で、正しい姿勢の記録 (正常な走行) の値の分布。オフライン評価 ([eval_localization_offline.py](../../tools/README.md)) を、重み 0 で流して、判定ごとの `score` の最大値を見る。
  - 突き抜けの割合が、正しい姿勢で十分に小さいか (例: 数 %)。
  - ずらし量が、正しい姿勢で 0 の近くに集まるか。
- 故障注入 (AMCL を飛ばす、少しずつずらす) で、検知までの時間が `submap_map` より短いか。短くなければ、足す理由がない。
- AMCL の姿勢での判定は、AMCL が同じスキャンと地図で推定しているので、独立な証拠にならない ([design.md](../../localization_supervisor/doc/design.md))。重みを下げ、`vouch` には使わない。

## やらないこと

- 屋外の地図のまま、しきい値を調整して使うこと。オフライン評価では、正しい姿勢でも異常と区別できなかった。
