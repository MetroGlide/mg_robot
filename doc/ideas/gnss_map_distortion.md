# 地図の歪みによる GNSS のずれを、信頼度に反映する

## 背景

地図の座標と GNSS (地球の座標) は、`gnss_transform.yaml` の 1 つの剛体変換 (x, y, yaw) で結んでいる。地図は SLAM で作るので、変換で吸収しきれない歪みが残り、GNSS は地図の座標と、場所によって一致したり、ずれたりする。
このずれは GNSS の故障ではなく、**場所ごとに決まった、再現するずれ**になる。GNSS そのものの誤差 (マルチパス、Fix の状態) とは性質が違う。

| | 地図の歪みによるずれ | GNSS そのものの誤差 |
| :--- | :--- | :--- |
| 何で決まるか | 場所 | 時間 |
| 同じ場所を別の日に走ると | ほぼ同じずれが出る | 毎回違う |
| 場所による変わり方 | なめらか (数十 m かけて変わる) | 急に変わることがある |
| GNSS が出す精度の値 | 含まない | ある程度は含む |

今の扱い:

- 自己位置の監督は、時間の窓で GNSS と EKF の残差を集め、GNSS の分散にかける倍率を出している ([design.md](../../localization_supervisor/doc/design.md#残差と分散の倍率))。窓なので、歪んだ区間に入ってから倍率が上がるまでに遅れる。
- GNSS だけがずれたと分かったときは、止めず、再初期化もせず、GNSS の分散を上げて使わないようにする ([mg_localization_supervisor](../../mg_localization_supervisor/README.md#gnss-だけがずれたとき))。
- 地図の座標に対する GNSS の信頼度を、場所ごとに前もって知ることはできていない。

## 構想

### 案 A: 場所ごとのずれの地図を、地図と一緒に作る

- 地図を作った走行のデータで、SLAM の軌跡と RTK の位置の差を、格子 (例: 数 m 角) ごとにまとめる。ずれの平均とばらつきを、地図の付属ファイルとして残す。
  - 計算は [eval_slam.py](../../tools/scripts/eval_slam.py) の `aligned` (全体を剛体で合わせた後の残差。地図の形の歪み) とほぼ同じ。
- 使い方は**補正ではなく、分散に足す**。ブリッジ ([nav_bridge.md](../../slam_gnss_2d/doc/nav_bridge.md)) が、今いる格子の「ずれの大きさの二乗 + ばらつき」を、`/odom/gps` の位置の分散に足す。
  - EKF は、歪みの大きい場所で GNSS を弱く使う。
  - 監督の GNSS の判定は、その場所で想定されるずれなら異常としない。
  - 復旧の候補の GNSS も、その場所では不確かとして扱われる。
- 地図を作り直したら、ずれの地図も作り直す。地図との対応を確かめられるように、作った地図の識別子を付属ファイルに残す。

### 案 B: 走行中の残差を、時間ではなく場所で集める

- 監督の `residuals` を、時間の窓ではなく、場所の格子ごとに集める。2 回目からは、歪んだ区間に入る前から倍率が分かる。走行のたびに、案 A のずれの地図を更新していくこともできる。
- 比べる相手は EKF ではなく **AMCL** にする。EKF は GNSS を含む融合の結果で、残差を小さく見積もる。AMCL はスキャンと地図だけで推定するので、「地図の座標で GNSS がどれだけずれているか」を直接測れる。
- AMCL がずれている間に集めると、誤りを学んでしまう。信頼できる周期で、AMCL を正しいと示す判定 (`vouch`) が正常なときだけ集める。

## 入る場所

- 案 A: ブリッジが `/odom/gps` の分散を作るところ。監督が出す倍率をかける処理 ([nav_bridge.md](../../slam_gnss_2d/doc/nav_bridge.md#外からの分散の倍率)) の手前に足せる。ずれの地図から足した分散は、監督が出した倍率とは別物なので、監督が標本から割り戻すことはない。判定では「想定されるずれ」としてそのまま効く。
- 案 B: 監督の `residuals` は、プラグインではなく中核の固定の処理なので、場所ごとの集計は、`residuals` に方式を足すか、プラグインにする必要がある。比べる相手を EKF から AMCL に変えるだけなら、設定の変更で済む (評価は要る)。

## 着手の前に確かめること

- **ずれが走行ごとに再現するか**。案 A が効くかどうかは、これで決まる。同じ地図で別の日に走った rosbag で、格子ごとのずれを走行間で比べる。実機は要らず、既存のツールの範囲でできる。
  - 再現する: 案 A を進める。
  - 再現しない (GNSS そのものの誤差が大きい): 案 B の時間の窓の方式を強める。
- 歪みが、位置合わせで吸収できるずれ (剛体の誤差) か、地図の形そのもの (曲がり) か。前者なら `gnss_transform.yaml` の見直しで足りる。
- 格子の大きさと、ずれの変わり方の関係 (なめらかさ)。

## やらないこと

- **ずれを引く補正**。場所ごとのずれを引けば GNSS を地図に合わせられるが、地図を作り直した後や、季節で植栽が変わったときなど、地図が変わるとずれの地図が古くなる。古い補正は、正しい GNSS を誤った方向に動かす。分散に足すだけなら、古くても「信頼を下げすぎる」側に倒れるだけで、安全。補正は、ずれの地図が走行ごとに再現すると確かめられてから検討する。
